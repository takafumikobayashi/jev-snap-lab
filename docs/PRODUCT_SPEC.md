# Product Specification

## 1. 概要

### プロダクト名

Jev Snap Lab

### コンセプト

> Tiny inputs. Instant decisions.

短い入力から、人間が一瞬で感じ取る複数の曖昧な属性を、Jev の構造化された判断として同時に返す実験用 Web アプリである。

### 目的

この MVP で検証するのは、次の仮説である。

1. 280文字程度の短文なら、1回の Jev 呼び出しで複数の判断を返しても待ち時間が体験を壊さない。
2. 文章生成ではなく、Choice / Score / Noul の組み合わせの方が短文の曖昧な特徴を直感的に見せられる。
3. 結果の数字だけでなく、候補分布・confidence・根拠データを見せると、AIの出力を「正解」ではなく「判断材料」として理解してもらえる。

## 2. 対象ユーザーと利用場面

- Jev の typed decision を試したい開発者
- 短文分類の UI / プロンプト設計を検証したいプロダクト開発者
- SNSや日常文章の曖昧な属性を遊びながら確認したい利用者
- CITY で、AIルーティングと根拠データの関係を確認したい利用者

データ入力はその場限りのデモを前提とし、ログインなしで利用できる。

## 3. MVP スコープ

### 含めるもの

- LOVE / SOCIAL / CITY のモード切替
- 最大280 Unicode code points の短文入力
- 1回の API 呼び出しで複数質問を fan-out
- Choice / Score / Noul の表示
- probability と confidence の区別表示
- Jev 応答時間、モデル ID、取得できた usage の表示
- CITY の担当候補と公式分掌情報への出典リンク
- timeout、認証エラー、rate limit、Jev 障害時の状態表示
- 入力の永続保存なし

### 含めないもの

- 入力履歴、共有 URL、ユーザーアカウント
- 入力文章の収集、歌詞データベース、検索、推薦
- 行政への送信、申請、通報、問い合わせ予約
- Jev からの自由形式の説明文生成
- CITY をM市の公式サービスとして見せること
- モデル出力を根拠にした自動アクション

## 4. 共通ユーザーフロー

1. ユーザーが LOVE / SOCIAL / CITY のいずれかを選ぶ。
2. 280文字以内の短文を入力する。
3. `JUDGE` ボタンを押す。
4. クライアントは `POST /api/judge` に mode と text を送る。
5. サーバーは入力を検証し、モードごとの質問群を組み立てて Jev API を1回呼ぶ。
6. サーバーは typed answer を UI 用の共通形式に変換する。CITY の場合は回答キーを根拠データへ join する。
7. ユーザーは結果カード、分布、confidence、レスポンス時間を確認する。

入力中にモードを切り替えた場合も、入力文は保持する。ただし送信中のリクエストは AbortController で中断し、新モードの結果と混ざらないよう request id を比較する。

## 5. 画面仕様

```text
┌─────────────────────────────────────────────┐
│ Jev Snap Lab                  Tiny inputs... │
│                                             │
│ [ LOVE ] [ SOCIAL ] [ CITY ]                │
│                                             │
│  短い文章を入力してください                  │
│  ┌─────────────────────────────────────────┐  │
│  │                                         │  │
│  └─────────────────────────────────────────┘  │
│  0 / 280                         [ JUDGE ]   │
│                                             │
│  RESULTS                                    │
│  ┌─────────────────────────────────────────┐  │
│  │ 判定カード / bar / gauge / YES-NO       │  │
│  └─────────────────────────────────────────┘  │
│  Response: 148ms · Model: jev-1.13.0       │
│  This is an experiment, not official advice │
└─────────────────────────────────────────────┘
```

### 共通コンポーネント

| 要素 | 仕様 |
|---|---|
| モードタブ | 3つのうち1つだけ選択。キーボードで移動可能。 |
| テキストエリア | `maxlength` だけに依存せず、サーバーでも280 code pointsを検証。改行は入力として許可する。 |
| 文字数 | `0 / 280` を表示。空白のみは送信不可。 |
| JUDGE | 空入力・送信中は disabled。送信中は `JUDGING...`。二重送信を防ぐ。 |
| 結果 | モード固有のカードを上から重要度順に表示。数字は0〜100%に丸める。 |
| confidence | Choice / Score のみ表示。probability と同じ意味の数字として扱わない。 |
| 補足 | 結果は確率的な判断で、現実の事実・公式判断・診断ではないと明示。 |
| 開示 | 入力がJevへ送信されること、アプリが保存・収集しないことを全モードで常時表示。**保存しないことと外部へ送らないことは別**なので、両方を書く。 |

### 配色

**色は「値の大小」ではなく「判断の種類」を示す。** Choiceの分布、Scoreの位置、Noulの独立したyes確率は意味の違う数値であり、すべて同じ色で描くと混同を招く。判定の種類ごとに1色を割り当て、カード内はその色と中立色だけで構成する。

| 種類 | 役割 | 表示 |
|---|---|---|
| Choice | 候補の分布（合計1） | 青。選択された候補を濃い段、他を淡い段 |
| Score | 順序尺度上の位置 | 橙。起点から現在位置までを塗り、位置に印 |
| Noul | 独立したyes確率 | 緑。YES側のみ着色し、NO側は中立色 |

**候補ごとに色を変えない。** CITYの担当課候補は最大28件あり、色相を回すと識別が破綻する。同一の問いの分布は1色で描く。

**色だけに識別を頼らない。** 各カードに種類を示す印と「選択肢 / 段階 / YES・NO」の文字を併記する。数値ラベルは常に表示する。

**文字は色を持たない。** ラベルや数値はink（前景色）のままにし、識別は印と図形が担う。低い確率をNOとして赤で表さない。

状態を示す色（低確度の注意など）は判定の色と別枠で、必ず印と文言を添える。色だけで意味を持たせない。

配色は3色ともライト・ダーク双方で色覚多様性を含む分離基準を満たすことを検証済み。ライトモードで緑のコントラストが3:1未満のため、Noulは数値ラベルの併記を必須とする。

### 表示ルール

- Choice: 選択された候補を chip で表示し、全候補の probability を横バーで表示する。上位3件を初期表示し、残りは `show details` で開く。
- Score: `score` の位置をメーターで示し、ラベルは `probabilities` 最大レベルの `legend` を使う。`score` はレベル間に着地する小数（例 1.05）なので `Math.round(score)` で `legend` を引かない。メーター両端に最小・最大レベルのラベルを添える。scoreを100点満点へ再計算しない。詳細な規則は [JEV_DESIGN.md](JEV_DESIGN.md) の §8。
- Noul: `YES 81%` と `NO 19%` を左右の比率で表示する。Noul は yes の確率であり、confidence ではない。
- Confidence: Choice / Score では `confidence 81%` のように別行で表示する。初期の視覚閾値は `< 0.60` を注意、`>= 0.80` を高いまとまりとするが、正答率を意味するものではない。
- 数値の小数: UI は原則整数%。内部 JSON は元の小数を保持する。
- 低確度: 結果を隠さず「判断が割れています」と表示する。MVPではconfidenceによって自動的に結論を差し替えない。

## 6. LOVE

### 体験

恋愛の短文を入力すると、単一の感情ラベルを断定するのではなく、恋愛的な読み取りの軸を横並びで見る。

例: `もう君のことは忘れたはずなのに`

表示イメージ:

```text
恋愛的な読み              未練 62% · 失恋 24% · 片思い 9%
まだ気持ちがある？        YES 92%
関係は終わっている？      YES 81%
恋愛シグナルの強さ        明確
判定のまとまり            0.78
```

1行目は `romantic_frame` Choiceの上位3候補の `probabilities` である（合計1になる分布の一部なので、各値は独立したYES確率ではない）。2行目以降のNoulは独立した軸なので、合計1にならず複数が同時に高くてよい。この2種類を同じ見た目のバーで並べない。

### 結果カード

| カード | 表示 | 意味 |
|---|---|---|
| Romantic reading | Choiceの上位候補 | 文面全体の主な恋愛的フレーム。`other / unclear`を必ず候補に残す。 |
| 恋愛的な強さ | Score meter | 恋愛に関する含意の強さ。感情の正しさではない。 |
| 軸別の読み | Noul bars | 熱愛、片思い、遠距離を独立に表示。複数が同時に高くなってよい。 |
| YES / NO | Noul | 「関係は終わっている」「まだ好き」など、明示した問いへのyes確率。 |

「失恋」「未練」は `romantic_frame` Choiceの候補（`breakup` / `lingering`）が担い、Noulでは重ねて聞かない。Choiceの分布とNoulの値は別の意味を持つため、画面上も別のカードに置く。

### UI上の注意

- 「作者が本当にそう思っている」とは表示しない。「この文面はそう読める？」に統一する。
- 著作権の注意をLOVEで常時表示する。ただし**入力を促す書き方をしない**。「歌詞を入力できます」と書くと著作物を貼り付ける行為を直接促すことになるため、「判定するのは文面がどう読めるかであり、作品の分析や評価ではない」という位置づけの説明にとどめ、取り扱いへの注意を添える。

  モードの説明文も同じ理由で「恋愛ソングの歌詞を分析」ではなく「恋愛ソングや詩など、文中の含意」とする。判定対象の文章の種類を例示するだけで、行為の指示にしない。
- 自傷、ストーカー、虐待などの安全上の判断はMVPの判定軸に含めない。必要になった場合は別の安全設計として扱う。

## 7. SOCIAL

### 体験

SNS投稿の短文を、人間がタイムラインで感じる複数の属性に分解する。positive / negative の一軸 sentiment analysis を主目的にしない。

例: `ChatGPT便利すぎてExcel開かなくなった`

表示イメージ:

```text
投稿の主な型              ネタ 72%
驚き                      YES 88%
学び・発見                YES 76%
ツッコミ待ち              YES 69%
カジュアル度              高い
自慢っぽさ                NO 81%
```

### 結果カード

| カード | 表示 | 意味 |
|---|---|---|
| Post type | Choice | 観察、ネタ、学び、意見、質問、告知、愚痴などの主な型。 |
| Social signals | Noul bars | 驚き、ユーモア、学び、共感誘発、自慢っぽさ、煽り、ツッコミ待ち。 |
| Discussion / casualness | Score | 議論性とカジュアル度をそれぞれ順序尺度で表示。 |
| Reaction invitation | Noul | 返信・引用・共感などの反応を誘う文面か。実際のエンゲージメント予測ではない。 |

### UI上の注意

- 「自慢」「煽り」は人格評価ではなく、文面からそう読める確率として表示する。
- 作者の意図、読者の反応、実際の投稿結果を区別する。
- ハラスメント・差別・誤情報の判定はMVPの主機能ではない。表示された属性をモデレーション判定として利用しない。

## 8. CITY

### 体験

住民が自治体へ伝えそうな短い問い合わせから、最初に確認すべき担当候補、カテゴリ、緊急度、現地確認や人の確認が必要そうかを表示する。

例: `家の前の防犯灯が切れてます`

表示イメージ:

```text
担当課候補                危機管理課 78%
次点                      建設課 12%
問い合わせカテゴリ        防犯・市民安全
緊急度                    近日対応寄り
現地確認が必要？          YES 84%
人による確認が必要？      YES 91%

根拠: M市「組織」ページ / 事務組織規則 第7条の2
※正式な行政案内ではありません。最終確認は公式窓口へ。
```

### 結果カード

| カード | 表示 | 意味 |
|---|---|---|
| 担当課候補 | Choiceの上位3件 | 現行の公式組織・事務分掌データの候補キーをJevが選ぶ。各候補に出典を付ける。 |
| 問い合わせカテゴリ | Choice | 組織改編で課名が変わっても比較しやすい安定カテゴリ。 |
| 緊急度 | Score | 通常、近日、当日、危険が迫る、の順序。行政のSLAや消防の緊急判断ではない。 |
| 現地確認 | Noul | 写真・位置・現場状態など人が現地を確認する必要がありそうか。 |
| 人による確認 | Noul | 事実確認、資格、個人情報、例外判断などが必要そうか。confidenceが低い場合もコード側で注意表示する。 |
| 他課連携 | Noul | 単独課だけでは終わらず、別課・外部機関との連携がありそうか。 |
| 根拠 | 静的データ join | Jevの自由生成ではなく、保存済み公式URL・条項・取得日を表示する。 |

### CITY固有の制約

- 画面のヘッダーまたは結果下部に「技術検証・デモ」「正式な行政案内ではない」を常時表示する。
- 担当課の表示は「候補」であり、問い合わせ先を自動確定しない。
- 緊急度が高くても、アプリが通報・連絡を実行しない。
- 根拠URLを表示できない候補は、`source unavailable` として候補の信頼度を下げるのではなく、明示的に「根拠データ未登録」と表示する。
- 根拠データの有効日を結果に含める。古いデータを最新情報として見せない。
- **公開用のデータセットは架空である。** 根拠表示では「根拠データ（架空）」と見出しを変え、実在の自治体の出典ではないことを明示する。API の `city.fictional` はデータセットの性質から導き、固定値にしない。固定値にすると架空データを公式根拠として扱う契約になる。

## 9. エラー・状態仕様

| 状態 | UI | ユーザー操作 |
|---|---|---|
| Idle | 入力とJUDGE | 入力して送信 |
| Validating | 入力欄のエラー | 280文字以下・空白以外に修正 |
| Judging | ボタンを無効化、短いローディング | 待つ。入力は保持 |
| Success | 結果カード | 再判定・モード切替 |
| Timeout | 「Jevから時間内に応答がありません」 | 再試行 |
| Rate limited | 「アクセスが集中しています」 | 少し待って再試行 |
| Jev unavailable | 「現在Jevへ接続できません」 | 後で再試行 |
| Invalid request | 開発者向け詳細を出さず一般メッセージ | 入力を見直す |
| Missing CITY source | 判定は表示するが出典欠落を警告 | 正式な窓口で確認 |

APIエラー時も、ユーザー入力をエラーメッセージへ埋め込まない。詳細な例外と入力本文をクライアントへ返さない。

## 10. アクセシビリティとレスポンシブ

- カードの色だけで確率を区別しない。数値、ラベル、バーの幅を併用する。
- `aria-live="polite"` で結果の更新を通知する。
- `button` / `textarea` / tab のフォーカスリングを常に表示する。
- モバイルでは1列、デスクトップではカードを2列までにする。
- 低い確率やNOを赤色だけで表現しない。
- 長い日本語ラベルでレイアウトが壊れないよう、折り返しを許可する。

## 11. MVP の成功条件

- 3モードを切り替え、280文字以内の入力を1画面で判定できる。
- 1回の送信で、Choice / Score / Noul を少なくとも各1種類表示できる。
- probabilityとconfidenceを混同せず表示できる。
- 入力例に対して、Jevのレスポンスモデル、usage、レイテンシ、エラー状態を確認できる。
- CITYで少なくとも「防犯灯」「道路・橋りょう」「ごみ」「水道・下水道」「戸籍・住民票」「子育て」の候補を公式出典付きで表示できる。
- APIキーがブラウザのJS、HTML、リポジトリに露出しない。
- 公式出典が存在しない結果を「公式回答」と誤認させない。

## 12. Semantic 拡張（実装済み）

### CITY Semantic Fit

CITYの既定経路は、現行の課レベル `route_to` Choiceとローカルの根拠joinである。Semantic Fitはその結果を置き換えず、上位1課の代表分掌を限定評価する。**実装済みだが本番では無効**で、有効にしても結果は画面へ出さず観測ログだけ残す。

- 1課あたりの分掌候補は12件を上限とする。
- 追加のJev呼び出しは最大1回。リクエスト全体の予算16,000msをStage 1と分け合う。
- Noulのyes確率は「分掌に意味的に適合する読み」であり、担当課の確定や公式確率ではない。
- 失敗時は現行のCITY結果へfallbackする。
- 実験候補と公式根拠は、既存と同じ安定IDでローカルjoinする。

詳細は [CITY_SEMANTIC_EXPERIMENT.md](CITY_SEMANTIC_EXPERIMENT.md) を参照する。

### SPEC FIND

SPEC FINDは、短い自然言語から固定コーパス内の仕様書passageを探し、章・節・ページ・公式PDFへの導線を表示するモードである。**実装済みで、本番で有効にする。** v0の範囲を次に限定する。

- デジタル庁の共通機能標準仕様書第2.7版の公式PDF
- オフラインで正規化した39件の代表passage
- 1回のbounded Jev requestと、passageごとの独立Semantic Fit Noul
- アプリ側での順位付けと、ローカル出典メタデータのjoin

PDF v0には機能要件Excel、項目定義書、API仕様書、ランタイムのWeb取得を含めない。結果は関連箇所の候補であり、仕様適合性・実装可否・行政上の正式判断ではない。詳細は [SPEC_FIND_DESIGN.md](SPEC_FIND_DESIGN.md) を参照する。
